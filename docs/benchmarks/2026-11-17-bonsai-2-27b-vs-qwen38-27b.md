# Local implementer comparison: bonsai-2:27b vs Qwen3.8-27B

**Date:** 2026-11-17
**Question:** Is `bonsai-2:27b` strong enough to complete most
implementation tasks when dispatched through the pipeline?

**Answer on this sample:** yes. It completes 10 of 12 cells (83%), ties the
strongest existing local 27B arm on success rate, lands no incorrect code,
and never times out. It is roughly 2.1x slower per cell, for reasons that are
a configuration (thinking + longer trajectories) rather than a size effect.

## Method

Every cell is one `(task, model, trial)` run through the real pipeline
(`ingest -> dispatch -> tests -> review -> merge`) inside a throwaway,
isolated workspace with a local bare `origin`. A cell is a **success** only
when the story reaches `done` (tests pass, review APPROVEs, the merge lands)
**and** an independent ground-truth suite, which the implementing model never
sees, passes against the merged code.

Grid: the same 4 tasks and 3 trials used for the `qwen38_27b` arm —
`lru_cache`, `lru_cache_rs` (Rust), `interval_merge_js` (JavaScript) and
`ratelimiter_bugfix` (Tier 2: fix a bug in seeded, pre-existing code without
breaking its suite) — 12 cells, sequential on one Ollama host.

| Arm | Model | Quant | Temperature | Thinking | Window | Dispatch budget | Steps |
|---|---|---|---|---|---|---|---|
| `bonsai2_27b` | `bonsai-2:27b` (26.9B, qwen35 arch) | Q2_0, 8.3 GB | 0.7 | `medium` (the tag's default) | 49152 | 1800s | 60 |
| `qwen38_27b` | Qwen3.8-27B (27.3B, dense) | UD-IQ3_XXS, 11 GB | 0.7 | `false` | 49152 | 1800s | 60 |

Non-dispatch roles (planner, test author, review, overlord) were held at the
baseline reviewer, `ollama/deepseek-v4.1-flash`, for both arms, so the
implementer is the only variable. Note the quantization differs: this measures
bonsai as shipped, not the architecture at equal precision.

## Results

Success = merged `done` **and** ground truth passing.

| Task | bonsai-2:27b | qwen38_27b |
|---|---|---|
| interval_merge_js | 3/3 (100%) | 3/3 (100%) |
| lru_cache | 3/3 (100%) | 3/3 (100%) |
| lru_cache_rs | 2/3 (66%) | 3/3 (100%) |
| ratelimiter_bugfix | 2/3 (66%) | 1/3 (33%) |
| **Total** | **10/12 (83%)** | **10/12 (83%)** |

| Arm | Merged | GT-pass | Merged-but-wrong | TDD-skip | Timeouts | Avg s | Avg ticks |
|---|---|---|---|---|---|---|---|
| bonsai2_27b | 10/12 | 11/12 | 0 | 0 | 0 | 985.6 | 88.8 |
| qwen38_27b | 10/12 | 12/12 | 0 | 0 | 0 | 459.2 | 41.4 |

**Merged-but-wrong is zero for both arms:** nothing the pipeline merged was
rejected by the independent suite.

## The two non-success cells

Both are process-level rather than capability failures, and neither is
incorrect code landing.

- **`lru_cache_rs` trial 0 — repetition-guard park.** After a repetition
  nudge, the agent re-edited its scratchpad instead of the implementation and
  was parked mid-work. The incomplete crate then failed to compile the
  ground-truth suite (`no LruCache in the root`), so the cell counts as a
  failure. This is the same read/repetition fixation seen in the Qwen3.6 arms,
  not a wrong-answer mode.
- **`ratelimiter_bugfix` trial 1 — empty review verdict.** The implementation
  is correct: the ground-truth suite passes 7/7 in the surviving worktree.
  But the shared reviewer returned `REQUEST_CHANGES` with no findings text
  twice, and the pipeline parked the story as inconclusive
  (`review inconclusive after 2 attempts`). This is a reviewer-output problem,
  not the model under test; the review role was deliberately held constant
  across arms.

## Why it is ~2.1x slower

The model is **not smaller in parameters** — 26.9B against Qwen3.8's 27.3B, the
same size class. The runtime difference comes from:

1. **Thinking is on.** `bonsai-2:27b` was pinned to `think=medium` (its
   default); the `qwen38_27b` comparator ran with thinking suppressed. Every
   tool-calling turn carries reasoning tokens before the tool call.
2. **Longer trajectories.** 88.8 average ticks versus 41.4, including steps
   spent probing the environment (`which python3`, `pytest --version`) before
   writing, and scratchpad churn. More turns over a 49k-token context also
   means more prompt reprocessing per cell.

Q2_0 quantization reduces weights and memory (8.3 GB) and does not by itself
make generation slower; it is the added reasoning and the extra turns that
account for the wall-clock gap. A `think=false` arm would be the clean test of
that explanation.

## Caveats

- 12 cells over 4 tasks; a one-cell difference between arms is not evidence.
  The project's 9-task grid exists for exactly this reason and is the better
  instrument for a tighter estimate.
- Quantization differs (Q2_0 vs IQ3_XXS), so this is "bonsai as shipped."
- The `ratelimiter_bugfix` failure is attributable to the shared reviewer, so
  the arms' 2/3 vs 1/3 split on that task is weak evidence.
- Prior local comparisons found the 4-task grid's per-arm numbers noisy; the
  conclusion here is limited to "completes most tasks at the 27B local tier,"
  not to a precise ranking against Qwen3.8.

## Reproduction

```bash
cd tests/benchmark
BENCH_TASKS="lru_cache lru_cache_rs interval_merge_js ratelimiter_bugfix" \
BENCH_TRIALS=3 \
  bash _runs/launch_arm.sh bonsai2_27b BENCH_BONSAI_TAG bonsai-2:27b \
  "$PWD/_runs/bonsai2_27b_4task"
```

The harness needed three repairs to run cells at all after the forge and
detached-review refactors (committed alongside this note): reviews must run
inline so the hermetic PR/CI stubs apply, `_ci_status_once` must be stubbed
alongside `_ci_status`, and the merge-readiness poll must be skipped for a
local-only remote.
