# UI family review

The third family review prompted by
[`backlog-family-review-correction_2026-10-19.md`](backlog-family-review-correction_2026-10-19.md).
It is the largest family in the backlog (37 plans, 244 stories) and, on
event-aware numbers, the third-weakest among families with 20+ stories —
118/228 first-pass clean (51.8%).

This review also tests the family assignment itself. The backlog review's
rule (`dashboard|chat|workspace|ui[-_]|static|event|server|w1|w2|w3|b1|b2`)
pulls in the W1/B-wave architecture plans and the event-driven-pipeline work,
which are not UI. The first section splits the bucket; the rest reads the
record.

**Coverage:** the 37 plans this family assigns, completed between the
2026-08-12 backfill and 2026-09-21.

Sources: each plan's `manifest.json`, `.notifications.jsonl`, per-story
`.journal.json`; the current `app/` and `static/` tree and its tests.

## 2. Findings

### 2.1 The bucket is two populations, and the UI one is not the weak one

UI proper is 57.3% clean; the architecture waves are 47.9%. The bucket rate
(51.8%) therefore describes the W1/B waves and the event-driven work, not the
dashboard/chat/workspace features. Any future comparison should split these
two; the keyword rule was written for coverage, not for a coherent family.

### 2.2 Step caps are not an on-device-only phenomenon in this family

Previous family reviews found step caps concentrated on the on-device tier.
Here the 60 cap stories split 28 on-device, 21 cloud-oss and 11 Claude
(out of population) — cloud-oss capped almost as often.

The cloud-oss caps cluster in the large multi-file refactors:
`dashboard-comms-toasts-live-updates` (4), `server-app-file-split` (4),
`event-driven-pipeline` (2), `event-driven-pipeline-phase3` (2),
`workspace-picker-wiring` (2), `chat-logs-usage` (2). These are the
multi-file split/refactor shapes
`agent-dispatch-story-sizing.md` already names as hard independent of tier;
routing them to cloud-oss reduced but did not remove the failure. The
on-device caps cluster in `w1a-extract-pipelineservice` (9) and
`event-driven-pipeline-phase3` (4), same shapes on the weaker tier.

### 2.3 The largest escalation cause here is "no new commit", not rework or caps

The sidecars carry 45 escalation notices: **19 no-new-commit, 17 rework
budget, 4 step cap, 5 other**. No-new-commit means the agent kept crashing
or parking without writing code — the work was larger than the executor could
finish in a dispatch. That is consistent with the concentration above: the
big plans are where agents stall. The later no-new-commit escalation path and
the same-target guard (PR #1127) changed how that stall is handled, but not
why it happens.

### 2.4 `W2_CHAT_ENTRY_POINT_PLAN` is the shared-artifact failure, already root-caused

W2's 9 stories split 3 clean / 6 not. The two cloud-oss escalations, `W2-03`
(wire plan-authoring tools) and `W2-05` (wire decision-answering tools), are
the stories `pipeline-story-schema.md` documents: an earlier story had pinned
the `SYSTEM_PROMPT`'s "Available tools: ..." sentence to the three tools that
existed then, and nothing could update it, so later stories failed a test
about a frozen snapshot.

The defect is fixed in the current tree: `app/chat.py` assembles that sentence
from the live `TOOLS` registry (`_available_tools_sentence`, `:314`), with the
2026-08-20 incident recorded in the comment above it. The prompt now names
every registered tool and its params, so the drift cannot recur. `W2-06`
(security gate) is Claude-backed and out of population; its `legacy_message`
is not a first-pass signal.

### 2.5 The UI code shipped and is covered

`app/chat.py`, `static/index.html`, `static/style.css` and
`static/app/main.js` are all present, and 134 test files match
chat/dashboard/workspace/static/ui. The family's losses are execution
failures on large stories, not gaps in what was delivered.

## 3. What this retro does not say

- It does not line-by-line review the dashboard/chat code; it verifies the
  shipped surface and reads the plans' event history.
- It cannot separate "large multi-file refactor" from "large file edited at
  1000+ lines" as the cause of the cloud-oss caps; both shapes appear in the
  same plans.
- It does not cover plans completed after 2026-09-21.

## 4. Recommendations

1. **Split the family assignment.** Record `architecture waves` separately
   from `UI proper` on any future family retro; the bucket's rate is not the
   UI's rate, and blending them hides that the UI features are above the
   overall average.
2. **Concentrate future review on the five big plans** — dashboard-comms,
   w1a, event-driven-pipeline-phase3, w1b, w1c — which hold half the losses.
   The 14 clean small plans need no attention.
3. **Treat the cloud-oss caps as evidence for the sizing rule.** Routing a
   multi-file refactor to a stronger tier helps but does not exempt it from
   the shape rules in `agent-dispatch-story-sizing.md`; split the story, not
   only the tier.
4. **No new work on the UI features themselves.** Nothing in the record shows
   a delivered feature failing; the W2 shared-artifact defect is already fixed
   and the prompt is registry-generated.
